## 2. Driver behaviour

### Sources

Cross-checked during this work against three public implementations, fetched on 2026-11-23:
- Adafruit_VL6180X: register addresses, all 30 AN4545 private settings and the public settings are **identical** to ours.
- The Linux kernel's `drivers/iio/light/vl6180.c`: addresses agree.
- Pololu's `vl6180x-arduino`: addresses agree, and it uses the same configuration registers as our explicit ones.

Still **[REVIEW]** against the ST datasheet and AN4545 themselves:
- **0x0E3 and 0x0E4:** Pololu writes `0x0E3=0x01` and `0x0E4=0x03`, where Adafruit and we write `0x00` and `0x04`.
- **Codes 1–5:** their exact meanings (Adafruit only calls them `SYSERR_1..5`).
- **Offset register:** whether 0x024 is two's complement.
- **Bits 7:6 of 0x04F:** the error bits of `RESULT__INTERRUPT_STATUS_GPIO`. **None of the sources confirms them**, so they are not used.

**Addressing:** 16-bit register addresses, high byte first, and 8-bit values. A read is one combined transaction (address write, then a read with a repeated start).

### `setup`

1. Read `IDENTIFICATION__MODEL_ID` (0x000). If it is not `0xB4`, return `-EPROTO` with **nothing written**.
2. If `SYSTEM__FRESH_OUT_OF_RESET` (0x016) is 1, write the 30 private settings, then write 0 to 0x016.
3. Always write the ranging configuration:
   - GPIO1 interrupt mode (0x011=0x10);
   - readout averaging (0x10A=0x30, about 4.4 ms);
   - VHV repeat rate (0x031=0xFF);
   - one VHV recalibration (0x02E=1);
   - "new sample ready" interrupt (0x014=0x24);
   - **max convergence 49 ms** (0x01C=0x31);
   - **interleaved mode off** (0x2A3=0);
   - **1x range scaling** (RANGE_SCALER 0x096/0x097=0x00FD).

   The last three used to be power-on defaults that the driver only assumed. The 100 ms deadline relies on the convergence time, and the "value is plain mm, 0–255" claim relies on the scaling.
4. Offset. **FACTORY** (the default) writes nothing. **SET** writes `offset_mm` to 0x024 and reads it back.
5. **Read back** every setting from step 3 except the self-clearing VHV trigger, then re-read 0x016. Any mismatch, or a fresh flag that did not stay cleared, is `-EPROTO` (IO_ERR in the sample). A device that does not hold its settings cannot be trusted. On real hardware, **[MEASURE]** that the readback passes (§4 step 2a).

### `range` (single shot)

1. Wait for device-ready (bit 0 of 0x04D).
2. Clear interrupts (0x015=7).
3. Start a range (0x018=1).
4. Poll until "new sample ready" (0x04F & 7 == 4).
5. Read `RESULT__RANGE_VAL` (0x062, mm) and `RESULT__RANGE_STATUS` (0x04D).
6. Clear interrupts again.

Clearing *before* the start means a result left over from an interrupted attempt is never returned. Adafruit's `readRange()` skips this step.

**Deadline:** 100 ms per measurement, with a 1 ms poll interval and a cap on the number of polls. A `static_assert` checks that it exceeds the max convergence plus averaging (about 53.4 ms). Both values are **[MEASURE]**; the probe's `attempt_us` distribution measures the real figure.

### Range error codes (bits 7:4 of 0x04D, Adafruit names)

| Code | Name | Kind |
|---|---|---|
| 0 | NONE | valid range |
| 1–5 | SYSERR_1..SYSERR_5 | **chip fault** (`oc_vl6180x_range_error_is_system`) |
| 6 | ECE_FAIL | early convergence estimate failed |
| 7 | NO_CONVERGE | max convergence time reached |
| 8 | RANGE_IGNORE | below the ignore threshold |
| 9, 10 | UNDEFINED_9/10 | not defined |
| 11 | SNR | signal too weak / ambient too high |
| 12, 13 | RAW_UFLOW / RAW_OFLOW | raw range under/overflow |
| 14, 15 | RANGE_UFLOW / RANGE_OFLOW | too close / too far or nothing in range |

## 3. Adapter: mapping to `oc_sample` and recovery

| Situation | status | value | aux |
|---|---|---|---|
| Range valid (code 0) | OK | mm (0–255) | raw range-status byte |
| Device-flagged range, code 1–15 | RANGE_ERR | 0 | raw range-status byte (code in bits 7:4) |
| `-ENXIO` / `-EREMOTEIO` | NACK | 0 | 0 |
| `-ETIMEDOUT` | TIMEOUT | 0 | 0 |
| Anything else, incl. `-EPROTO` (wrong model ID, readback mismatch) | IO_ERR | 0 | 0 |

**When setup runs again.** Setup runs on the first attempt, and on the attempt after any of these:
1. **Any failed attempt** (bus error, timeout, failed setup). This is unplug/replug recovery.
2. **A chip fault** (code 1–5). The sample is still RANGE_ERR with the raw byte, so the contract is unchanged.
3. **A silent reset.** Every attempt on a set-up device starts by reading 0x016, which costs one extra read **[MEASURE]**. A brownout, or an unplug and replug between two attempts, resets the chip without any failed transfer. Before this check the reader would have kept ranging without ST's mandatory settings. The soak's "unplug a sensor for ten minutes" fault and the demo-day unplug both go through path 1 or path 3.

**Counters** (`oc_distance_get_stats`): attempts, setups, setup_failures, silent_resets, system_errors, io_failures, and ranges per error code. They exist for heartbeat and log lines, but nothing prints them in the reader process yet (that code is Alan's; see §6).

## 4. Live procedure on the Pi (evidence)

Wire or rewire only with the power off, and check the 3.3 V rail with a multimeter first (CLAUDE.md, "Electrical safety"). Capture everything **raw and unedited**:

1. `ls -l /dev/i2c-*` and `i2cdetect -y 1`. **0x29** should appear, and 0x48 too if the ADS1115 is connected. If 0x29 shows as `UU`, a kernel driver has claimed it; remove that overlay, or the probe gets `EBUSY` (IO_ERR).
2. Run `make probe`, then `./build/plain/distance_probe /dev/i2c-1 200 100 | tee probe-$(date +%F-%H%M).csv` and keep the stderr summary. Runs:
   - **(a) Readback check.** The first rows must be `OK` or `RANGE_ERR`, not `IO_ERR` with `errno=Protocol error`. If every row is IO_ERR/EPROTO, the readback (§2 step 5) disagrees with the real part. Stop there and report it with the output; don't paper over it.
   - **(b) Known distances.** Hold a flat target at ruler-measured distances (for example 30, 60 and 100 mm). Expect OK, matching mm, a small `stddev`, and `position` becoming `STABLE` when the distance is inside 15–120 mm.
   - **(c) Movement.** Move the target slowly during a run. Expect `MOVING`.
   - **(d) No target.** Expect `RANGE_ERR` with `range_err=RANGE_OFLOW` or `SNR` and `position=NO_TARGET`, not a made-up distance.
   - **(e) Unplug VIN mid-run and plug it back in** (only if the wiring makes that safe). Expect NACK rows, then OK again, with `setups` increasing and no restart.
3. **Calibration (optional, recommended once the shroud exists).** Hold a flat, light-coloured target at 50 mm and run `./build/plain/distance_probe --calibrate 50 /dev/i2c-1 50 100 | tee cal.csv`. Then re-run with `--offset <suggested>` at the same distance and check that the mean is now about 50.
   - The suggestion is `current + (known − mean)`. It needs at least 10 OK samples and a spread of no more than 10 mm, otherwise it reports `too_noisy_target_moved`.
   - The reader process still uses the factory offset; there is no flag for it yet (§6).
4. `dmesg | tail -50` after the runs.
5. Copy `m3-live-2026-10-30-115327/` from the demo into the repository as raw evidence, if it still exists on the Pi.

**What this shows:**
- the real driver, adapter, `oc_sample` mapping and position verdict on a LIVE bus;
- the real `attempt_us` distribution (p50/p95/p99/max);
- whether the readback, the RANGE_ERR codes and the replug recovery behave the way the host tests assume.

**What it doesn't show:**
- the reader process, IPC or storage (`m3_demo.sh` covers those);
- the sample rate under load;
- accuracy beyond a ruler check.

Running the probe on a machine without the sensor (for example a laptop with its own `/dev/i2c-1`) gives NACK rows labelled LIVE. Those are live *attempts*, not distance readings, and must never be presented as sensor evidence.

## 5. Placement and stability gate (`oc_position`): **[REVIEW: Alan]**

CLAUDE.md requires the VL6180X to "verify sensor placement and detect movement during capture". DESIGN.md §7 gives sensor fusion to Alan. Kacper decided (2026-11-23) to write the *verdict* on the distance side and leave the *use* of it to Alan. The module is pure: it gets samples and a "now", and nothing else.

- **Window:** the last `window_n` consecutive OK samples of one unbroken stream. Any non-OK sample, seq gap, duplicate or regression (u32 wrap-safe), or backwards timestamp empties it. Seq and time breaks are counted as `discontinuities`.
- **Verdicts,** first match wins:
  1. `UNAVAILABLE`: no sample; the newest is older than `max_age_ns`; or it is NACK/TIMEOUT/IO_ERR.
  2. `FAULT`: RANGE_ERR with code 1–5.
  3. `NO_TARGET`: any other RANGE_ERR.
  4. `SETTLING`: fewer than `window_n` OK samples.
  5. `OUT_OF_RANGE`: median outside [min, max].
  6. `MOVING`: max − min > `max_spread_mm`.
  7. `STABLE`.

  Only `STABLE` should let an automatic reading be called position-validated.
- **Provenance:** the verdict's origin is LIVE only if every sample in the window is LIVE; otherwise it is the window's common origin, or MIXED (DESIGN.md §4).
- **Defaults** (**[MEASURE]** placeholders): 15–120 mm, 5 mm spread, 5 samples, 500 ms age. They depend on the shroud geometry and the real sample rate.

## 6. Open items and decisions for Alan's review

1. **`oc_position` (§5):** API, use in fusion, defaults.
2. **`aux` = the whole `RESULT__RANGE_STATUS` byte, or 0 when the device produced none.** IMPLEMENTATION_NOTES §1 says "raw VL6180X status code [MEASURE]"; this is a concrete version of that.
3. **Chip faults (codes 1–5) stay RANGE_ERR**, distinguishable through `aux`, rather than becoming IO_ERR. Changing that would change the shared status contract.
4. **The errno table duplicates `oc_light_status_for_errno`** in `oc_distance_status_for_errno`. Proposal: one shared copy in `oc_sample` later.
5. **Re-setup triggers (§3)**, including the extra fresh-check read on every attempt.
6. **Sample rate.** DESIGN.md §1 targets 10–20 distance samples/s, but the LIVE default period in `src/oc_role.c` is 150 ms (about 6.7/s; the demo's 201 samples in 30 s match that). A single-shot range needs at most about 55 ms, so 100 ms (10/s) should fit **[MEASURE]**. This is Alan's code and is not changed here.
7. **Not plumbed into the reader process (Alan's code):**
   - an offset option for `--role distance` (the reader uses FACTORY);
   - printing `oc_distance_get_stats` in STAT/SUMMARY and heartbeats.
