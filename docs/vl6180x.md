# VL6180X distance reader

Owner: Kacper (DESIGN.md §7). `DESIGN.md` and `docs/IMPLEMENTATION_NOTES.md` §1 (the `oc_sample` contract) are authoritative. This file records how the distance reader implements them, the decisions that need Alan's review, and the procedure for getting live evidence.

**Status: host-tested only.** The driver, the adapter and the probe exist, and `tests/test_distance.c` passes against a **simulated** VL6180X. **No reading from a real VL6180X has been taken yet.** M3's "genuine live readings" requires running the probe on the Pi (§4) and recording its raw output.

## 2. Driver behaviour

Register addresses, the mandatory settings and the timing come from the ST VL6180X datasheet and application note AN4545. They have **not** been checked against the datasheet in this repository **[REVIEW]**.

**Addressing:** 16-bit register addresses, high byte first, and 8-bit values. A read is one combined transaction (address write, then a read with a repeated start), which is what the Linux kernel's `vl6180` IIO driver also does.

**`setup`:**
1. Read `IDENTIFICATION__MODEL_ID` (0x000). If it isn't `0xB4`, return `-EPROTO` with **nothing written**, so the driver never writes to a device that isn't a VL6180X.
2. If `SYSTEM__FRESH_OUT_OF_RESET` (0x016) is 1, write AN4545's 30 mandatory "private" settings, then write 0 to 0x016.
3. Always write the ranging configuration: GPIO1 interrupt mode, readout averaging, VHV recalibration, and the "new sample ready" interrupt (0x014 = 0x24).

**`range` (single shot):**
1. Wait for device-ready (bit 0 of 0x04D).
2. Clear interrupts (0x015 = 7).
3. Start a range (0x018 = 1).
4. Poll until "new sample ready" (0x04F & 7 == 4).
5. Read `RESULT__RANGE_VAL` (0x062, mm) and `RESULT__RANGE_STATUS` (0x04D).
6. Clear interrupts again.

Clearing *before* the start means a result left over from an interrupted attempt is never returned.

**Deadline:** 100 ms per measurement, with a 1 ms poll interval and a cap on the number of polls. Both are **[MEASURE]**. The datasheet default max convergence time is about 49 ms, plus about 4.3 ms of readout averaging. The probe's `attempt_us` column measures the real figure.

## 3. Mapping to `oc_sample`, and decisions for review

| Situation | status | value | aux |
|---|---|---|---|
| Range valid (error code 0) | OK | mm (0–255) | raw range-status byte |
| Device flags the range (error code 1–15, e.g. 11 max SNR / no target, 15 overflow) | RANGE_ERR | 0 | raw range-status byte (code in bits 7:4) |
| `-ENXIO` / `-EREMOTEIO` | NACK | 0 | 0 |
| `-ETIMEDOUT` | TIMEOUT | 0 | 0 |
| Anything else, including `-EPROTO` (wrong model ID) | IO_ERR | 0 | 0 |

**For Alan's review:**

1. **`aux` = the whole `RESULT__RANGE_STATUS` byte, or 0 when the device produced none.** IMPLEMENTATION_NOTES §1 says "raw VL6180X status code [MEASURE]"; this is a concrete version of that.
2. **The errno table is the same as `oc_light_status_for_errno`, but duplicated** in `oc_distance_status_for_errno` rather than calling the light function. Proposal: move one shared copy into `oc_sample` later.
3. **Re-setup after a failure.** The attempt after any failed one runs `setup` again. A re-plugged (power-cycled) sensor therefore gets its settings back without a reader restart. This bears on the "unplug a sensor for ten minutes" soak fault.
4. **Timestamp:** read after the attempt, including any setup, exactly as for light.
5. **Not done:** the reader *process* (HELLO, the socket to the hub, heartbeats). It depends on Alan's IPC and supervisor (Mechanism E) and was not touched.

## 4. Live bring-up on the Pi (evidence for M3)

Wire or rewire only with the power off, and check the 3.3 V rail with a multimeter first (CLAUDE.md, "Electrical safety"). Then capture each of these **raw and unedited**:

1. `ls -l /dev/i2c-*` and `i2cdetect -y 1`. **0x29** should appear, and 0x48 too if the ADS1115 is connected. If 0x29 shows as `UU`, a kernel driver has claimed the device (for example a `vl6180` overlay); remove that overlay, or the probe gets `EBUSY` (IO_ERR).
2. `make probe && ./build/plain/distance_probe /dev/i2c-1 50 100 | tee probe-$(date +%F-%H%M).csv`. Keep the stderr summary too. Three runs:
   - **(a)** a flat target held at a few known distances (for example 30, 60 and 100 mm, measured with a ruler);
   - **(b)** nothing in front of the sensor (expect RANGE_ERR, not a made-up distance);
   - **(c)** unplug the sensor's VIN mid-run and plug it back in (expect NACK rows, then OK again with no restart). Don't hot-plug if the wiring makes that unsafe; otherwise skip (c).
3. `dmesg | tail -50` after the runs.

**What this shows:**
- every printed sample went through the real driver, adapter and `oc_sample` mapping, from a LIVE bus;
- the real `attempt_us` timing, which checks the 100 ms deadline;
- whether RANGE_ERR and NACK show up the way the host tests assume.

**What it doesn't show:**
- the distance reader *process*, IPC, or storage (M3's "through the real pipeline into real storage" needs the hub);
- the sample rate under load;
- accuracy beyond a ruler check.

Running the probe on a machine without the sensor (e.g. a laptop that happens to have `/dev/i2c-1`) gives NACK rows labelled LIVE. Those are live *attempts*, not distance readings, and must never be presented as sensor evidence.
